# Archive extraction repair and verification

September 28, 2026. Implements the next work in [the release follow-up plan](RELEASE_FOLLOWUP_PLAN.md). Source changes target 0.1.7; preserve the verified 0.1.6 artifact and leave the owner's installed 0.1.5 unchanged. No public release, signing purchase or assurance approval is implied.

## Observed dependency and trust boundaries

- The sole resolved `extract-zip` consumer is `@electron/packager` 18.4.4, used by Forge 7.11.2. Its `dist/unzip.js` calls the default function with only an absolute `dir`. Electron 44.4.2 already uses `@electron-internal/extract-zip` 1.0.5 elsewhere in this dependency tree.
- Official packager 20.3.0 uses the new extractor, but its hooks accept objects/promises rather than the callback signatures Forge 7.11.2 provides. Do not force that major upgrade into the current Forge lifecycle. Instead evaluate a scoped extractor substitution while retaining the packager API, then exercise the actual CommonJS wrapper on the pinned Node runtime.
- Packager 18.4.4 downloads through `@electron/get` 3.1.0. Both downloaded and cached files are checksum-validated by default. `electronZipDir` bypasses that path; supplied checksums, checksum-disable flags, custom downloaders and mirror/environment settings can alter trust. Packager creates a unique extraction subdirectory, but its default parent is predictable/shared across its invocations.
- The replacement's [security policy](https://raw.githubusercontent.com/electron/extract-zip/v1.0.5/SECURITY.md) supports trusted, checksum-verified Electron distributions used through Electron tooling. Attacker-preseeded destinations and general untrusted archives are outside its supported scope. The application does not use this dependency to import users' calendar files.

## Exact changes and acceptance gates

1. Preserve the versioned 0.1.6 installer, audit/SBOM/summary and hashes under ignored release/evidence directories before rebuilding. Increment source to 0.1.7. Add only a scoped `@electron/packager` override from `extract-zip` to the pinned Electron implementation 1.0.5; review every lockfile change. No blanket alias or audit suppression.
2. Add a build policy for the currently supported Windows x64/Electron 44.4.2 target. Pin the archive SHA-256 from the official release checksum file: `6aae435b6cd5c0eedf9fd38824bae4045ffdaecd029f0b8c8328bac3f5b71f03`. Require the manifest's Electron version to match. Refuse custom local archive directories, alternate download configuration and mirror/custom-version environment overrides before packaging. Pass the pinned digest into the real downloader, including cache validation. Future Electron/platform changes require a reviewed new digest and evidence.
3. In the Forge pre-package hook, validate policy and create a unique temporary build parent. Let packager create its normal fresh child inside that parent. Successful post-package cleanup may remove only the directory created and retained by that same process after checking its resolved identity and containment. Never enumerate or remove unrelated build roots. A failed build may retain its own root for inspection; do not search/delete previous roots automatically. This does not defend against a compromised account modifying build code or files concurrently.
4. Use independently authored, tiny ZIP fixtures inside unique test roots. Through the actual packager extraction wrapper verify nested bytes, existing regular-file replacement, path traversal/absolute/reserved-name rejection or safe containment, duplicate entries, relative safe symlinks, outside/absolute/chained symlink targets, duplicate link names, pre-existing leaf links and parent directory junctions. All sentinels and potential destinations must remain inside the test root but outside the extraction child. Assert bytes and resulting paths, not rejection alone. Test symlink creation capability explicitly; never label an unsupported positive symlink case passed.
5. Exercise the real `@electron/get` with an in-memory fixture downloader: good download, valid cache hit without a new download, corrupt cache followed by replacement, and corrupt fresh content rejected before extraction. No external test endpoint or large archive. Verify rejected build options/environment/target versions have no filesystem effects; repeated build hooks get distinct roots and successful cleanup stays scoped.
6. Run all tooling tests, credential/type/unit/build checks, cloud emulator tests, Windows native package/Squirrel maker, archive scan and the 25 desktop cases. Generate full audit/SBOM; an unexpected new finding still blocks. Once the local gate passes, use that same blocking gate in CI and attempt evidence upload even on failure. Require fresh GitHub Windows installation/build/test results. A zero npm audit is limited dependency evidence, not native Electron/Chromium review or a product compliance opinion.
7. Record exact source/installer/ASAR/lockfile/evidence identities, test counts and any platform skips/failures. Update the draft PR, risk register and maintenance steps. Keep operator policy, manual/second-PC, signing, broader abuse defenses and independent assurance gates open.
