October 1, 2026. The owner reported disabled sign-in again and requires working sign-in after each version update. Inspection found only the intentionally unconfigured isolated security-test copy running; the installed application was not running. Close that owned copy normally and restore the ordinary installed app for the owner. Preserve its private environment, calendar and remembered account; no version change is needed to correct which copy is open.

## Ordered verification and release gate

1. Identify open copies by executable and explicit test-profile arguments. Never infer installed-app health from a development/test window, terminate broad process groups, or copy personal sessions into synthetic fixtures. Close only the owned unconfigured test copy. Do not leave an unconfigured test window open as the owner's normal app.
2. Through the ordinary Windows desktop context, resolve the physical installed executable and `%APPDATA%/C.C. Lime/.local/.env`. Reject redirected or unexpected physical targets. Verify exact expected version and retained artifact identity, local environment presence and unchanged private configuration. Preserve keys outside source, renderer bundles and installers. Do not print their values.
3. Start the actual installed executable with a new isolated profile supplied only with the verified private environment file. Observe the actual renderer: configured/googleConfigured true, both sign-in buttons enabled, no remembered session or personal calendar. Close normally, restart the same isolated profile, and require the controls again. Record exact executable/archive identity and normal exit. Delete the fixture's environment copy after the check. A configured fixture is availability evidence, not proof of successful Google consent/token exchange.
4. Add CI controls using synthetic configuration without real keys: configured email/Google controls enabled through restart, and absent configuration honestly disabled without exposing Node APIs or browser credentials. Keep these checks in baseline and all-seven-fuse compatibility coverage. This prevents future renderer/runtime changes from silently disabling valid sign-in. CI has no production credentials and cannot prove live authentication.
5. Verify live email/password sign-in with a disposable identity and cleanup; use human browser completion for actual Google sign-in where required. Never ask for the owner's password or alter it as a test. Record availability, live provider/service and interactive Google results separately. A visible button alone cannot close authentication acceptance.
6. Reopen the stable installed launcher normally, without test-profile/debug flags, after isolated verification. Confirm the ordinary installed process/window is the copy left for the owner. If a test copy is needed later, clearly identify it and close it after testing.

No update may be reported complete until normal-context configuration preservation, fresh installed controls and restart checks pass. Interactive authentication gaps must be stated explicitly; missing configuration must be repaired privately before claiming success. Apply this gate even when isolated installed calendar tests pass. Existing availability checks that used the redirected tool context are insufficient. See [local configuration](LOCAL_CONFIGURATION.md) and [production acceptance](PRODUCTION_ACCEPTANCE_MAP.md).

The [normal-context Windows gate](../scripts/verify-installed-signin.ps1) runs the [external renderer verifier](../scripts/signin-readiness.mjs) on the actual installed executable. Use the version and pinned Node executable for the release being checked. Reports remain under ignored test-results; private values never appear in console output. [CI regressions](../tests/production/signin-readiness.spec.ts) use synthetic configuration only, and workflow policy rejects removal of this file from combined-hardening coverage. Test fixtures verify fingerprints and all-seven/header policy at both starts and delete their private environment copy after closure.
