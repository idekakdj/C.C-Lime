# Password-change sign-in requirement

October 2, 2026. Owner request: require a new sign-in after changing a password and verify that another device's older session also requires sign-in. This is a source change; installed 0.1.16 and the normal owner's account/profile are not test fixtures.

## Implementation and acceptance order

1. Preserve current-password verification, account identity/generation checks, new-password strength/confirmation, provider cooldowns and local limits. Wrong passwords, rejected updates and canceled operations must not report success or sign out an unrelated account.
2. After a successful provider password update, discard all returned credentials. Clear the current in-memory and remembered session using the existing durable sign-out path. Do not adopt or persist the update's replacement tokens. Stop account reminders/sync and hide account data; retain SQLite and pending edits for the same account's next sign-in.
3. Put a non-sensitive sign-in notice in the session snapshot, so the explanation survives renderer account-state changes that dismiss toasts. Clear the notice on explicit sign-in or ordinary sign-out. Warn before submission that password changes require signing in again.
4. Validate the provider refresh token before every automatic/manual sync pass, including unverified accounts, before cloud reads or writes. Keep existing 30-second foreground / 120-second background polling and retry/provider cooldown behavior. A revoked refresh token must clear the remembered session and show a sign-in explanation; a network failure must preserve the session and pending edits. Recheck stopped/account state after the awaited validation.
5. Add regressions for successful change/durable restart, wrong current password/provider rejection, identity races, remembered-file deletion failures, notice/form behavior, two separate device sessions and pending-edit preservation. The second session must fail refresh, clear local login, reject the old password and reconnect using the new password. Prove that the sync preflight prevents any cloud reads/writes once revocation is detected.
6. Run unit/UI/type checks and authentication/Firestore emulator tests. Verify production Firebase with an isolated disposable email/password identity and two independent encrypted session directories if access permits; do not change the owner's password. Retain sanitized counts/results only and delete the disposable identity and test sessions. Distinguish emulator behavior from actual provider revocation semantics.
7. Build the source and run the existing sign-in renderer checks appropriate to these changes. Record evidence, source/installed separation and limits in implementation documentation. No version bump or installation is included in this request.

## Security limits

Implementation and acceptance completed: source check (265 unit/UI plus 81 tooling passing/two existing symlink skips), three additional service integration checks and typecheck, 59 emulator cases, production-provider six-check disposable-account verification/cleanup, build/package secret inspection, and three independent desktop password-form/sign-in readiness cases. The emulator does not implement refresh-token revocation after password updates; it verifies data preservation while actual provider behavior is verified separately. See [retained implementation evidence](IMPLEMENTATION_STATUS.md). No release installation or immediate backend access-token rejection is claimed.

Provider password changes expire existing refresh tokens. Offline computers detect revocation only after reconnecting. Updated clients check at the next scheduled sync (normally 30 seconds visible / 120 seconds background, plus network latency and retry/cooldown), on startup, and on manual sync. This does not promise immediate revocation of an already issued access token in a modified/older client: Firebase access tokens can remain valid up to their one-hour expiry unless backend revocation enforcement rejects them. No privileged key, new server or rules deployment is needed for this bounded client-side behavior. Local calendar files remain on disk after sign-out; this is access/session handling, not disk encryption or remote erasure.
