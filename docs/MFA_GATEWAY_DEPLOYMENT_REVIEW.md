## Exact proposed pilot resources

One owner-controlled Cloudflare Free account, one Worker `cc-lime-auth`, one D1 database `cc-lime-auth-pilot`, hourly cleanup and a stable `https://cc-lime-auth.<chosen-subdomain>.workers.dev` origin. The RP ID is that **entire hostname**, not `workers.dev`; do not select it until the owner account/subdomain exists. Passkeys are bound to this RP and cannot be silently moved to a different domain. Preview URLs stay disabled. No third-party analytics, account emails, request bodies or credentials enter application logs. Cloudflare operational metadata and its processing locations still need vendor/privacy review.

The blank [Wrangler example](../gateway/wrangler.example.jsonc) is intentionally non-deployable. Create the actual config only in ignored `.local`: set the exact project/origin/RP, real D1 ID/binding, production entry `gateway/src/worker.mjs`, workers.dev enabled only for the approved stable origin, preview URLs/observability disabled, and the existing hourly trigger. Never deploy `gateway/tests/runtime-worker.mjs`; it has a synthetic identity verifier. The production build bundles only the real server entry.

Use the `0001.sql` schema for a new empty staging database. It has no deployed predecessor to migrate. Do not overwrite a live database with this initial schema. Account/credential/challenge statements use bound parameters. Public credential keys, stable random user handles, counters, backup flags and labels are stored server-side; no passkey private keys or biometric data are collected. Challenge/rate records expire and are removed hourly.

## Privileged signing custody — explicit trust boundary

The current candidate uses a dedicated Firebase service-account PKCS8 signing key in a **Worker secret binding**, never a desktop variable, browser asset, public Wrangler file, GitHub secret/artifact or committed `.env`. No such key has been created or uploaded. This creates a new privileged custodian: compromise of the signing identity can impersonate Firebase users, and compromise of Firestore administrative access can bypass ordinary client rules. A pilot UID allowlist reduces application exposure; it does not constrain a stolen private signing key. Keyless federation is not implemented and is not represented as available automatically on the free plan.

Before creating the key, review the service account, its owner/deputy, permitted access, Cloudflare administrator MFA, secret storage, rotation/revocation procedure and provider terms. Start from a custom role with `firebaseauth.users.get` for authoritative status/factor/revocation lookup. Gateway gate reads/writes/deletes also need corresponding Firestore entity permissions. Verify the exact minimum permissions with the staged real calls; do not grant Owner, Editor, Firebase Admin or Authentication Admin for convenience. Firestore IAM does not provide the application's document-level `authSecurity/*` isolation, so these permissions can expose broader project data. Isolating the revocation store or changing the trust architecture remains an option to review before acceptance.

Secret bindings are `FIREBASE_SIGNER_EMAIL`, `FIREBASE_SIGNER_PRIVATE_KEY`, high-entropy `RATE_LIMIT_SECRET` and a private JSON `PILOT_UIDS` list (1–20 UIDs). The template contains blanks only. Use local secret entry/upload tooling that does not echo values or put them on a command line/history. A generated key is a real administrator secret and needs explicit custody approval after this review; general feature implementation is not evidence that its risk has been accepted.

## Native authenticator prerequisites

[Firebase TOTP](https://firebase.google.com/docs/auth/web/totp-mfa) requires Firebase Authentication with Identity Platform, verified email and a supported provider. [Firebase documents Spark support after the Identity Platform upgrade](https://firebase.google.com/docs/auth), but the actual project's ability to activate TOTP without linking billing still requires read-back and a disposable live enrollment test. Never enable billing or SMS to make the test pass. Stop dependent activation if a paid plan is required.

Prepare a minimal TOTP-only config change: MFA enabled, TOTP provider enabled, supported adjacent intervals selected after provider review, phone/SMS settings left unchanged/deferred. Preserve current provider/password settings and the exact private baseline. Independently read back billing before and after any approved change. No owner enrollment/removal is automated. The source flag `CC_LIME_TOTP_ENABLED` indicates tested provider readiness; it cannot enable the provider by itself.

Password accounts enroll native TOTP **before** adding passkeys. This protects the existing direct password endpoint against attacker-controlled factor enrollment. Passkeys remain an alternative future sign-in with user verification, not a fake native TOTP claim. Adding a native authenticator uses recent native password/TOTP or Google confirmation; a custom passkey token is not used to claim native MFA support. Last-passkey removal is denied if no other passkey/TOTP remains. Native factor removal/recovery outside the app requires separate provider tests and operator controls.

## Resource ceilings and availability

[Workers Free](https://developers.cloudflare.com/workers/platform/pricing/) lists 100,000 requests/day and 10 ms CPU/invocation. [D1 Free](https://developers.cloudflare.com/d1/platform/pricing/) lists 5 million rows read/day, 100,000 rows written/day and 5 GB total storage. These are ceilings, not a promise this cryptographic workload meets the CPU budget. Measure real hosted registration/assertion/JWT signing, cold starts, row amplification and cleanup before activation. Local workerd timing is not production CPU evidence.

The source applies durable 30 attempts/minute/IP, 10/minute/UID and 10,000 API attempts/day globally. IP keys are HMAC-derived. Unknown routes return 404; page requests, failed D1 operations and requests before the quota check still consume platform capacity. An attacker can exhaust the pilot's free capacity or shared-campus-IP quota. Free-plan failure must deny authentication safely while preserving local calendar changes. Do not auto-upgrade plans. Review emergency disabling, aggregate failure monitoring, owner notifications, D1 restore and recovery evidence before required rollout.

## Deployment sequence and completion evidence

1. Owner creates Cloudflare Free account, secures its login and supplies the chosen account/subdomain through normal local authentication. Do not send passwords/API tokens in chat.
2. Complete native TOTP read-only feasibility and the exact provider/IAM/rules/config review. Record existing billing disabled, backup provider/rules, signing custody decision and explicit narrow activation authorization.
3. Create a private staging D1/Worker and approved secret bindings. Verify only the expected RP origin works, previews are disabled, synthetic test entry is absent, and there is no accidental paid subscription.
4. Use disposable accounts only for live native enrollment/sign-in, bad/replayed codes, cancellation, refresh, password change, linked Google behavior and factor removal. Independently verify signed provider claims; cleanup identities and all data. Never use emulator/mock claims as this evidence.
5. Test real Windows Hello/phone/security key on the stable HTTPS origin. Verify Firebase custom-token exchange produces the exact same UID/version/epoch/fixed expiry, refresh retains the one-hour assurance deadline, and old sessions fail after credential removal/password change on two devices. Test raw REST reads and transactions, not just UI controls.
6. Measure CPU/free quotas, unavailable mirror/D1/provider behavior, cleanup jobs and restore. Document measured revocation delays: D1 and Firestore are not a distributed transaction. A failed mirror publication denies new token issuance/management, but an already-issued raw token may remain usable until the rules marker updates or its fixed expiry. No immediate universal revocation claim is made.
7. Provide recovery: at least two independent factors before owner enforcement; establish loss-of-all-factors identity verification and controlled administrative recovery. No automated recovery-code or email-bypass feature exists. Password reset alone cannot remove native TOTP.
8. Package a compatible, separately requested release. Verify private configuration plus email/Google fresh startup/restart after installation; complete actual authentication separately. Enroll the owner deliberately and prove both methods/recovery work before setting required mode.
9. Derive/review the staged rules using `scripts/passkey-rules-candidate.mjs`, retaining ownership/schema/write quota/receipts/deletion behavior. Apply only after compatible installed release and recovery are confirmed. Record live bypass tests and rollback; never deploy candidate rules to an unprepared owner account.

## Deletion, retention and rollback

Deleting an account keeps the existing order: calendar deletion protocol, Firebase identity deletion, local account cleanup. The server hourly reconciler performs a successful administrative lookup before treating an identity as deleted; disabled/unverified users and provider failures are not deletion. It removes credential keys/labels and bound flows in a D1 transaction, rotates/publishes the denial marker, retains a minimal UID/user-handle/epoch/cutoff tombstone for 24 hours, then rechecks deletion and erases the gate/account with provider preconditions. Fair batches check up to 20 accounts per run. Failed gate/lookup/erase operations remain pending for retry. This is eventual cleanup, not immediate erasure, and provider/D1 backups/Time Travel need an approved retention policy. Do not reuse Firebase UIDs during the tombstone/recovery process.

Rollback must preserve an enrolled user's protection: rolling back to password-only cloud rules reopens access, so it is not the automatic response to a passkey outage. Disable the gateway or stop new registrations, retain native TOTP, and deploy only a compatible tested rules/app rollback. Revoke a compromised signing key, rotate the gate for affected UIDs and verify raw access denial. Keep private evidence/backup securely, with no credentials in public reports.

This technical preparation does not establish SOC 2, ISO 27001, CAN/DGSI 118, PIPEDA or NIST assurance certification. PHIPA remains excluded. Organizational/legal/independent assessment and existing release-security gaps remain in the [compliance checklist](COMPLIANCE_CHECKLIST.md).
