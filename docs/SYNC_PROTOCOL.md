# Cloud transaction proof

The desktop uses a verified Firebase identity with Firestore REST requests. It has no administrator credential. Paths are isolated under `users/{uid}`; the emulator rejects cross-account reads and unverified writes.

An atomic commit contains one to four domain-record writes, one immutable receipt, and one sync-head write. All records have the same incremented logical sequence and mutation UUID. Each record carries its prior `updateTime` precondition (or `exists:false` for a create), and the head carries its own precondition. The head and receipt name exactly the participating record IDs. Rules check all participating writes with `getAfter`. The four-record/six-document shape passed against the Firestore emulator with the committed rules.

Before retrying an ambiguous request, the adapter reads the mutation receipt. A matching receipt and unchanged resulting records acknowledge the original logical change. Reusing a mutation ID with different data fails. A newer record produces a conflict rather than silently adopting that record as the local proposal's base.

Firebase may evaluate authorization against a concurrently advanced head before reporting a failed precondition. A permission denial is retried only when a separate read proves that the head changed; a changed domain record is a conflict. A denial with an unchanged head remains an error, except an independently confirmed saturated quota becomes a transient wait. Retries are bounded to five head races per attempt.

## Account write budget (0.1.3 protocol)

The head includes `rateWindowStart` (timestamp) and `rateWindowCount` (integer 1–60). Initial or reset windows must use server REQUEST_TIME and count 1. Reset is allowed only once 60 server seconds have elapsed. Keeping the old window with an exact +1 counter is allowed even after it expires, until its budget is exhausted; this conservative option avoids a clock-boundary race. Early reset, missing/partial counters, fabricated times, decrement and a 61st accepted commit are denied by rules. Active accounts cannot delete the head to reset the budget. Deletion remains separately authorized and resumable.

The client reads the quota on the existing CAS head. A reset uses a timestamp transform; retaining a window preserves the server timestamp's full precision. The response Date header estimates server time with a one-second safety margin. Exhaustion pauses sync while local changes remain pending. Receipt recovery does not submit a duplicate commit and consumes no additional quota slot. Racing devices re-read the head and share the same account budget. Each accepted group consumes one slot, whether it has one or four records; the policy permits bursts and is not a sliding-window requests-per-second limit.

Old heads without either quota field migrate on the first 0.1.3 write. **The new rules reject 0.1.2 and older writers. Upgrade all pilot clients before rule deployment.** No SQLite schema migration is involved; saved local queues must be preserved. Restoring older rules would remove this protection and is not an ordinary compatibility workaround.

Provider HTTP 429 and local request safeguards produce a monotonic cooldown. Manual sync, resume/focus and new saves cannot shorten the sync engine's hold. The shipped main process also limits repeated sensitive commands. These measures do not impose custom remote budgets on Firestore reads or Firebase account creation, nor on privileged administrative calls. See T-53 in the security/privacy plan for the remaining remote abuse controls.

Pull captures a high-water sequence, queries `(lastCompletedSequence, highWater]`, orders by sequence then record ID, and pages using both fields. A record edited beyond the high-water mark will be read on the next pass. The completed cursor advances only when the pass finishes; replaying an interrupted page is harmless. Tombstones retain their sequence and remain visible to offline devices. An explicit undo can restore a tombstone only against its current version; a stale edit/delete conflict is restored under a new identity.

The ordinary queue uses single-record groups. Linked changes such as detaching an occurrence persist their group membership in SQLite metadata and use up to four records per cloud commit. A group is acknowledged locally in one transaction, and a lost response retries the same group identity. Larger linked changes split into groups of four; bulk import is a locally atomic batch with resumable ordered cloud mutations and can be visible progressively on another device. Related cloud records are fetched before rendering a completed pull.

All 36 cases passed on September 26, 2026, including 60 real accepted commits, raw REST rejection of slot 61 and forged counters, concurrent final-slot allocation, legacy migration, expired-window reset, receipt replay and maximum-reminder rule budget. The prior protocol also passed live two-profile convergence/conflict/cleanup.
