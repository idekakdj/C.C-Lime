# Normal-launch sign-in configuration repair

September 30, 2026. The owner's fresh 0.1.10 screenshot shows disabled email/password and Google controls with the missing-Google-configuration message. Earlier isolated checks copied a valid configuration into their own profiles; they did not prove configuration availability to the owner's normal launch. This report supersedes the earlier explanation attributing the screenshot to Settings discoverability.

1. Identify the running executable, normal profile argument and configuration timestamps. Validate private environment files without printing values. Resolve actual open-file identities, rather than trusting logical AppData paths. Inspect persistent variable presence only. Do not read or log passwords/tokens or alter account databases.
2. Use a hidden, read-only diagnostic launched through the Windows desktop shell to observe the normal user's filesystem context. Require a fresh uniquely identified result written inside ignored test-results; resolve the real environment file and report only existence, variable-presence booleans and its hash. Fail if the observed context still resolves to the tool's redirected AppData copy. No account authentication is submitted by this step.
3. If the normal profile is missing configuration, copy only the validated private environment bytes into its own `.local/.env` through that same context. First validate destination under the exact normal C.C. Lime profile, retain a private backup if an existing file must change, reject a different configured project, and use atomic replacement. Never copy calendar data or remembered sessions between profiles and never embed credentials in an installer, source or renderer. If the file already matches, investigate the actual runtime rather than overwriting identical configuration.
4. Prepare any necessary source fix only after the failure is reproduced. Preserve environment override semantics, development/isolated-profile boundaries, account storage, and Google PKCE/state behavior. Show a truthful missing-cloud-configuration message instead of suggesting that only the Google client is unfinished. Run meaningful regression checks for the reproduced failure and configuration exclusion.
5. Require ordinary tray closure before restarting the owner's app. Verify fresh startup through the normal Windows launcher/context, enabled email and Google controls and preserved data/settings. Do not claim a real successful authentication until the owner or an authorized synthetic account actually completes it. A needed changed application binary must receive a new version and package/installed acceptance.
6. Record exact findings, repair and limits, update the draft PR if source changes, and resume the existing security work. Keep previously accepted profile/theme features and compliance gaps separate.

## Reproduced cause and repair

The tool-context logical environment path physically resolves into a redirected Codex AppData copy. A simple in-process Shell.Application launch still inherited that context and was rejected as sufficient evidence. Launching the read-only helper through Explorer's desktop automation object reproduced the normal-profile missing file at 22:15 UTC. This context distinction explains why an isolated supplied-configuration check passed while the owner's fresh launch showed disabled buttons.

At 22:16 UTC the normal-context repair created only the missing private environment file with exact previously validated bytes. It rejects a differing existing configuration instead of overwriting it. Read-back resolves to the actual ordinary profile and confirms required field presence and matching bytes. No calendar/session/settings files or executable were modified. The owner is asked to quit/reopen normally; enabled-control and actual-authentication observations remain distinct and pending that interaction. A source loader change is unnecessary for this reproduced setup issue.
