# Profile and appearance release plan

September 29, 2026. User priority: complete installed 0.1.9 acceptance, implement these features, then resume the production-security work. The user explicitly chose account synchronization for profile photos, profile names and custom themes. Ship changed application bytes as 0.1.10; preserve the tested 0.1.9 installer and private upgrade backup.

## Product behavior and data contract

1. Add a Profile destination reachable from the sidebar account card and header avatar. Show the saved photo or initials, editable display name, joined date and lifetime completed-task count. Keep the account email and provider identity read-only. Local preview remains a separate local profile.
2. Obtain a signed-in account's joined date from identity-provider account creation metadata when available. Preserve that date in the encrypted session; never substitute today's date and call it the account's joined date. Show an explicit unavailable state for older offline sessions. For local preview, label the durable first-use date as local-profile creation.
3. Store profile and appearance as a bounded, fixed-identity record inside the existing account-owned SQLite/outbox/Firestore protocol. Use its existing offline queue, conflict review, verified-email requirement, ownership rules, write quota and account-deletion path. Never publish photos or store upload source paths. Account profile conflicts must not offer a duplicate-profile outcome.
4. Select PNG or JPEG through the native file picker. Limit source bytes to 5 MiB and dimensions to 4,096 by 4,096 before native decoding; reject malformed/unsupported headers and symbolic links. Decode, center-crop and resize to a 128-pixel square PNG, removing original metadata. Limit the stored PNG data URL to 100,000 characters. Permit replacing/removing the icon. A cancelled picker or failed validation preserves the old image. Recheck account identity after the asynchronous picker before saving.
5. Define lifetime tasks consistently with the existing task list: tasks, assignments, exams and study sessions. Count each item or recurring task occurrence only once when completed, even if later reopened or deleted. Persist small deterministic completion records with no titles/notes; insert them transactionally alongside local completion writes. Re-completion and multi-device delivery cannot double-count the same identity. Seed available completed history on upgrade; clearly disclose that previously deleted history cannot be reconstructed. The statistic is personal progress, not an audited credential.
6. Add three built-in themes in Settings: Purple & black, Black & white, and Navy & gold. Keep Purple & black as the default. Built-in themes cannot be renamed or removed. Theme selection and saved custom palettes sync with the profile.
7. Provide labelled background, surface and accent color pickers with hex inputs, a preview and an explicit Save action. Generate readable foreground/focus/border colors from the selected palette. Allow at most three named custom palettes; enforce the limit in shared validation and Firestore rules, not just the UI. Allow applying, editing and deleting a slot; deleting the active slot selects the default preset. Unsaved drafts never silently replace the saved theme. Reject invalid colors, empty/oversized names, duplicate slot IDs and unknown active selections.
8. Apply appearance across navigation, calendar, settings, dialogs, inputs, hover/focus states and notices. Preserve semantic task/course colors. Do not use a global hue filter. Keyboard controls, narrow layouts and visible focus must remain usable; auto-selected text colors must pass the specified contrast checks.

## Implementation order and verification

1. Complete installed 0.1.9 data/shortcut/notice checks and all existing desktop tests. Retain recovery evidence before new runs. Record the successful prior tooling CI separately.

Define backup behavior: same-account backups retain profile/history; foreign calendar transfers must not overwrite another account's identity or historical progress. Older clients must be upgraded before consuming the new record types.
3. Implement bounded photo validation and native conversion behind one allowlisted command. Add a separate upload attempt limit and preserve existing cloud quotas. Test invalid images, excessive sizes/dimensions, cancellation and an account switch during selection.
4. Implement deterministic completion retention, restart durability, deletion/reopen behavior, duplicate delivery and available-history initialization. Verify storage failure rolls back the triggering completion. Avoid adding unbounded arrays/counters that race across devices.
5. Extend Firestore validation for exact profile/theme/completion shapes and limits. Test valid writes, cross-account denial, oversized/invalid images, fourth palette rejection, malformed colors and unchanged quota enforcement. Run the entire emulator suite before deploying any rule change.

Test all presets, custom save/apply/edit/delete, three-slot cap, reload persistence, account switching and keyboard operation. 7. Run type/unit/tooling/cloud checks, dependency and credential gates, package/native/notice inspection and full desktop acceptance. Exercise profile/photo/palettes/completion history through two synthetic synced accounts/profiles, conflict handling, restart and deletion; remove synthetic cloud data afterward. Preserve no personal photos in Git or test artifacts.
8. Deploy only the tested additive rule update after backing up and comparing the current rules; verify deployed bytes and live ownership/quota behavior. Build and retain 0.1.10 with exact hashes. Any owner installation requires normal app closure, a fresh private baseline and preservation verification. Do not describe source/package checks as installed acceptance.
9. Update data inventory, retention/backup notes, risk register, release notes and PR evidence. Resume the independent production-fuse acceptance work after the requested feature gates pass. Certification and legal claims remain unapproved.

## Acceptance conditions

SQLite schema 2 is introduced with a pre-migration snapshot, preventing older local clients from accepting unknown record types. Full backups containing profile/completion records use version 2; version 1 remains readable. Calendar copies exclude profile/history even within the same account; same-account merge includes them subject to the existing no-overwrite rule. Backup UI discloses photos and lifetime history. Local first-use is labelled “Profile tracking since.” The owner installation follows the [0.1.10 upgrade gates](UPGRADE_0110_PLAN.md).

No fourth saved custom theme is possible through UI or direct cloud writes. A photo selected on one signed-in computer appears on another after normal sync and survives restart. A completion counted before deletion remains counted after deletion and sync, without counting re-completion twice. Joined date is honest about source/availability. Invalid uploads leave the profile intact. Switching accounts shows only that account's profile/history/palettes. Existing calendar, reminder, recovery and quota tests continue to pass.
