# C.C. Lime vulnerability and edge-case assessment

October 2, 2026. Owner-authorized engineering assessment of source based on `bfc4f03494ef18d5294cb97ffa1bd95238e266a4` and separately packaged Windows test copies. The normal installed 0.1.16 app, its profile, account, cloud configuration and production rules were not replaced. Version remains 0.1.16. This is not an independent penetration test or certification.

## Findings and repairs

Severity below is an engineering impact estimate, not an independently assigned CVSS score. Repairs are in source and the isolated test package; they are not installed updates.

| Finding | Trigger and impact | Repair and regression |
| --- | --- | --- |
| A-01: nonexistent local times can disrupt calendar/reminder expansion — medium availability | A saved deadline at Toronto's March 8, 2026 02:30 clock gap, an invalid occurrence override, or an all-day record on Apia's skipped December 30, 2011 date could throw during expansion. Deadline recurrence also counted the nonexistent date. | Validate new single/group/imported writes before transactions; skip impossible recurring local times and count valid occurrences consistently; contain older invalid anchors so other entries/reminders work. An app warning opens affected master/override editors for repair. Read schemas still accept older records so recovery does not discard a whole calendar. |
| A-02: duplicate occurrence overrides produce an ambiguous import — low integrity/availability | Two VEVENTs with the same UID and RECURRENCE-ID were accepted into preview. Domain expansion depended on file order; a database uniqueness failure could reject an otherwise useful import. Existing transactions prevented partial commits. | Keep the first valid override and explicitly warn/skip duplicates, using normalized occurrence identity. |
| A-03: UTC recurrence identity can target the wrong local occurrence — medium integrity | A Toronto 23:30 series with a UTC RECURRENCE-ID on the following UTC date was matched to that following civil date. An override could change the wrong repetition. Wrong-time identities on the same date were also accepted. | Normalize to the parent's zone, check DATE versus DATE-TIME type, confirm membership in the series and compare the actual original instant. Unsupported or mismatched identities are reported in import warnings. |
| A-04: imported seconds were dropped from repetitions — low integrity | Expanding a timed recurring event with nonzero seconds rebuilt its start from hours/minutes, shifting subsequent starts and preventing exact override matching. | Preserve original seconds and milliseconds while applying the local date and fixed elapsed duration. Test imported seconds through expansion, override matching and export/import. iCalendar export uses its supported whole-second representation. |
| A-05: selected calendar/backup files could grow past their checked size — low local availability | Calendar and backup readers checked size, then performed an unrestricted synchronous read. A growing/replaced regular file could invalidate the pre-read size decision. This was a code-path finding reproduced with deterministic file-growth fixtures, not a remote exploit. | Read through one descriptor, require regular files, reject selected symlinks/directories, recheck descriptor size and enforce an actual byte cap while reading. Caps remain 10 MiB for calendars and 50 MiB for backups; growth past a cap rejects and closes the descriptor. |

Original DST/duplicate tests failed before repair. The midnight/wrong-time and seconds regressions each failed before their repair. Atomicity tests verify rejected new times leave both records and the outbox unchanged. Growth fixtures cover changes before opening and after both stat checks; only limit-plus-one bytes are read in the latter case.

## Test evidence

The local evidence lives under ignored `test-results/` folders and contains synthetic data only. Do not upload private `.local` configuration or owner profile files with it.

- Source: all 285 tests passed in the final full run with one worker and an explicit 15-second per-test budget; type checking passed. Report: `test-results/adversarial-unit-verified.json`. Earlier 282-test full run passed before the final matrix/seconds regression. A later default-budget run had two password UI failures following a five-second typing-test timeout; the unchanged four-test password UI file passed when run independently. Keep these failed attempts as evidence; the longer budget changes no functional assertions.
- Calendar matrix: 144 deterministic combinations across six item types, three timing modes, four time zones and two DST-adjacent dates. All 112 supported combinations round-trip times, dates, duration, text and status, and repeated import is idempotent. The 32 unsupported all-day/deadline class/study combinations explicitly reject. A malformed-calendar corpus tests invalid dates/times, oversized fields, duplicate UIDs, unsupported/extreme rules, attachment-looking text and prototype-looking data.
- Cloud: all 59 existing Firebase emulator tests passed. Coverage includes owner/unverified-account denial, schema limits, direct malformed writes, transactional write quotas, receipt/deletion behavior, concurrent-device conflicts and authentication/sync cases. These are local demo-emulator results, not a new production policy deployment or provider abuse test.
- Native photos: real Electron decoder, 22 synthetic files; nine accepted image files and 13 malformed/oversized files rejected. Accepted files produce bounded 128 × 128 PNG icons for all 162 tested crop/zoom/edge combinations. Cases include 1 × 1, 1 × 4096, 4096 × 1, 4096 × 4096, portrait/landscape, actual JPEG with a misleading filename, truncated PNG, forged headers, invalid JPEG and appended data. App quits normally. Report: `test-results/avatar-adversarial/43b6dd9d-d409-4222-a460-88260af4557f/report.json`; reproducible command: `node tests/native/avatar-adversarial.mjs`.
- Tooling: 81 tests passed; two privilege-dependent extraction cases explicitly skipped. Release/CI policy fixtures, archive/path traversal, pinned build inputs, bounded loopback FTP and package-integrity checks are included.
- Supply chain: release dependency audit/SBOM covered 1,126 components with zero reported npm findings at this checkpoint. That is a dated registry result; it does not establish comprehensive Electron/Chromium/SQLite native security.
- Secrets/package: tracked/publishable-file scan passed; package check inspected 234 ASAR entries, ten dependency notices and 23 covered source files. No credentials/local configuration were packaged.
- Packaged app: 42 distinct tests passed across a full run and targeted retries. The final full run passed 36/41; four process/shutdown timeouts and one new test's attempt to fill collapsed Notes controls failed. The corrected test opens Details & reminders through the actual UI; all eight targeted checks passed, including those five failures, two repeated hostile/legacy checks and one added legacy-override repair case. Reports: `test-results/adversarial-packaged-final.json` and `test-results/adversarial-packaged-retry.json`. No timeout was accepted as a pass or forced exit counted as normal acceptance. New probes exercise actual literal event/profile text and restart, eleven invalid IPC requests (including cycles, BigInt, oversized payload and unknown commands), valid requests after rejection, and repair of legacy master/override times through renderer controls. Existing tests cover frames/service workers, protocol 404, Node boundaries, fuse positive controls, calendar views, crowded days, completion history, courses, profiles/themes, repetition and fresh/restart sign-in readiness.

Baseline source's GitHub push/PR runs `37076651013` and `37076655529` both completed successfully. ## Boundaries and remaining work

- Native computer control exposed only the owner's normal app window. It was left alone. The test executable was opened and exercised through the isolated Electron/Playwright harness; no native picker, tray, Windows notification, installer, Google-consent or physical second-PC acceptance is claimed here. The initial preview was closed normally before rebuilding.
- Most account races and provider-error cases use synthetic providers/emulators. Actual password-session evidence from the preceding task remains in [the session-change plan](PASSWORD_SESSION_CHANGE_PLAN.md); no owner-password or live Google-consent flow was exercised here.
- Current-device forced sign-in and refresh-token validation before sync do not immediately invalidate an already-issued ID token at the backend. Prior disposable live-account testing demonstrated this remaining window. Firebase documents one-hour ID tokens and separate server-side revocation checks. Finish approved server enforcement before claiming immediate revocation of all cloud access. [Firebase session documentation](https://firebase.google.com/docs/auth/admin/manage-sessions).
- Shipping/installed Electron fuse hardening, signing, clean-machine upgrade/OS acceptance, native advisory/provenance work and an independent attack assessment remain release gates in [the compliance checklist](COMPLIANCE_CHECKLIST.md) and [native review](NATIVE_SECURITY_REVIEW.md). One isolated candidate or npm scan does not close those gates. Electron recommends defense across renderer isolation, IPC, navigation and package fuses. [Electron security guide](https://www.electronjs.org/docs/latest/tutorial/security).
- Local calendar SQLite files/backups are not newly encrypted by these changes. Token storage encryption and account separation do not provide calendar-file encryption against the Windows account holder or a compromised OS.
- Supported input dates are 1900–2100; finite conversion supports only explicitly chosen ranges. Infinite or unfamiliar recurrence syntax is not newly made compatible by this assessment. There is no claim of exhaustive calendar-standard support or exhaustive malformed-image coverage.
- No remote production load test, OS/browser exploit chain, external infrastructure penetration test, continuous monitoring deployment, organizational audit, SOC 2 report, ISO 27001 certificate, CAN/DGSI 118 certification or legal compliance conclusion was produced. PHIPA remains outside the agreed personal-calendar scope.
