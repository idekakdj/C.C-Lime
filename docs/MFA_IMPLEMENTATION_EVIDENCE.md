## Implemented source controls

Native TOTP challenges suspend the original main-process operation until provider finalization returns a cryptographically verified, same-project/same-UID native TOTP identity. Password-only enrollment state has no calendar, sync, reminders, cloud-token access or remembered login. Enrollment-only downgrades remove older saved full sessions. Cancellation, account generations and five-minute deadlines guard late replies. Six-digit leading-zero codes work; errors/requests are bounded and provider cooldowns remain active. Local QR/manual setup secrets are transient, not snapshots, databases, diagnostics or backups. Successful enrollment forces a fresh factor sign-in.

The passkey gateway verifies actual WebAuthn registration/assertion signatures with the reviewed library, exact HTTPS RP/origin/challenge, user presence/verification, credential/user-handle binding, algorithms/counters/backup properties and one-use D1 state. Browser tickets contain no Firebase identity token/password. Desktop S256 proof and loopback state bind the one-use TLS exchange. The server checks verified UID/provider status/revocation, limits the owner-only pilot to a private UID allowlist, and issues an actually signed two-minute Firebase custom token carrying a fixed one-hour passkey assurance. Desktop independently checks Firebase signature/project/UID/custom proof/epoch/expiry. Refresh status distinguishes revocation (sign out) from an unavailable backend (keep offline data, refuse the unverified online result).

Passkeys are an alternative **sign-in** after native authenticator enrollment for email/password users, not independent password-only setup. Review found the direct native password/factor-enrollment bypass risk; both UI and server reject password-backed passkey registration/access without native TOTP. Adding native TOTP requires native password/TOTP or Google confirmation, not a custom passkey token. Loss/removal of upstream TOTP ends password-backed gateway access. Google-only policy remains explicit and is not a claim of upstream Google MFA.

Management requires recent full account proof, has five-credential capacity and an atomic last-factor removal guard. Credential removal/password-change gateway requests rotate a server-owned epoch/cutoff before subsequent issuance. Candidate cloud rules reject first-factor passwords, phone-only, anonymous, unverified, arbitrary custom and forged client flags while preserving calendar ownership/schema/quotas/receipts/deletion. Raw old custom tokens are rejected after the server marker rotates. D1 and Firestore mirror updates are not one distributed transaction; publication failures and provider-originated changes retain a disclosed stale-token window until the gate updates or fixed expiry. No live immediate cross-device revocation claim is made.

Hourly account-deletion reconciliation requires authoritative successful provider absence, transactionally removes credentials/bound flows, publishes a denial gate and retains a minimal 24-hour retry tombstone before final erasure. Disabled/unverified identities and failed/malformed lookups are not deletion. Fair batches and durable retries include former pilot users. Vendor backups/Time Travel retention and operational monitoring still require review; eventual cleanup is not instantaneous erasure.
