Preserve the two-column wide layout, single-column narrow layout, scrolling and all themes. Long names/email text must wrap without pushing cards outside the workspace. 2. Split native photo selection from saving. Keep the existing regular-file, 5 MiB, PNG/JPEG and 4,096-pixel validations before decoding. Keep the original decoded image only in main-process memory while editing. Return a metadata-free, bounded preview and opaque token, never the original file path or original bytes. No source photograph is written to SQLite/cloud/backup.
3. Provide a labelled square crop modal after selection, with a live preview, drag positioning, keyboard-accessible horizontal/vertical sliders, zoom from 1× to 4×, reset, Save photo and Cancel. Start centered at 1×. Shared deterministic geometry clamps/validates square coordinates inside the original image at all aspect ratios; small images remain valid and resize to 128 pixels. Preview matches the source-space square used by the native final crop.
4. Apply the final crop in the main process from the retained native image, resize/re-encode as a 128×128 PNG, enforce the existing 100,000-character avatar limit, then save through the existing profile/outbox transaction. Save only after explicit confirmation; cancellation/Escape/invalid image must preserve the old icon. Emit the saved toast after durable commit, not after picking a file.
5. Bind the draft to its active LocalStore, unique token, current photo and ten-minute expiry. Only one selection intent/draft is current. Reject stale, malformed, expired and switched-account commits; clear memory on cancel/removal/account transition/close. Preserve edits to profile name/themes made while cropping. Keep a valid draft retryable if the durable write fails. Apply existing photo selection rate limit before the picker and a bounded commit budget. Do not accept image bytes or paths in crop-commit payloads.
6. Add meaningful geometry, service draft/cancel/stale/account/failure tests and native normalization checks. Update desktop upload tests for explicit crop saving; verify offset/zoom, cancellation, saved dimensions, restart persistence and account/photo isolation. Verify centered gutters and no overflow at wide/narrow sizes, chevron removal, keyboard controls, automated A/AA checks and visually inspect isolated screenshots in the preset themes.
7. Run source/credential/type/unit/tooling/cloud/build/package checks and original plus independent desktop acceptance on new bytes. Keep the remaining production-fuse/OS/dialog/compliance gaps explicit. Update privacy inventory/user guide and evidence without claiming original photos are retained or all native UI paths are independently automated.
8. Retain a checksummed 0.1.11 installer and inspect its archive exclusion/notices. Before an owner upgrade, require ordinary tray closure and a fresh backup/comparison through Explorer's normal desktop context with physical profile-path verification, fixing the previous redirected-profile verification mistake. Preserve every account's records/settings/private configuration; install only the retained tested bytes and verify normal-launch sign-in. User-visible functionality and real account authentication are distinct checks.

## Additional account requirements (September 30, 2026)

- Expose the existing synced display-name field as Username in Profile. It is an editable private profile label, not a unique login handle; email remains the login identifier. Preserve existing names and avoid a record/schema migration.
- Centralize a password policy and confirmation validator shared by renderer and main process: 15–128 Unicode characters for newly created passwords, allow spaces/paste/password managers, reject a bounded local list of predictable passwords and repeated patterns. Provide advisory strength feedback locally without sending passwords to a scoring service. This estimate and small blocklist do not constitute comprehensive breached-password screening or certification. Existing-password login/reauthentication validation remains unchanged.
- Account creation and adding a password to a Google account both require new password twice. Do not add confirmation or strength requirements to existing-password sign-in. Clear new-password fields on mode changes, successful operations and unmount; never save them in storage, diagnostics or logs.
- Add Change password in Settings for password-enabled accounts, including accounts that also linked Google. Google-only accounts continue to manage their Google password with Google and can explicitly add a separate password using the validated form.
- Change password requires current password plus matching new password twice, with the same strength feedback. In one exclusive auth operation verify current password with the provider, enforce the same account UID and session generation, then update using the fresh token and accept rotated credentials. Wrong current password, mismatched/weak new passwords, sign-out/account changes and rate limits must not update another account. Never include passwords in result/errors. A provider update can succeed despite a later network failure; explain retry/re-login behavior in the guide.
- Rate-limit password changes before network effects. Verify rejected requests never reach update, provider mismatch/cancellation isolation, rotated-session persistence and real emulator login with new password/old-password rejection. Cover signup confirmation and Settings visibility without mutating the owner's account. Firebase-hosted email reset UI remains provider-managed and outside this app form.
- References: Firebase REST Auth https://firebase.google.com/docs/reference/rest/auth and NIST length/passphrase guidance https://pages.nist.gov/800-63-4/sp800-63b.html . Full provider policy enforcement, independent assurance and comprehensive breached-password screening remain security follow-ups.

## Acceptance gates

- Profile heading/cards share a centered content boundary with nonzero gutters; no horizontal overflow or clipped buttons at 800, 1,000 and wide desktop viewport sizes. Both columns align on wide screens. Bottom profile chevron is absent.
- Native selection opens a crop preview; moving/zooming changes the preview and final square. Save persists only the selected 128×128 icon. Cancel, Escape and failed selection keep the prior photo across restart.
- Invalid token/geometry, stale photo/account, expiry and overlapping selection cannot save a wrong photo. Successful name/theme updates are retained when a crop is committed. Failed storage retains the old icon and allows an in-session retry.
- Credentials stay in ignored private environment files, and source/photo drafts remain out of SQLite/cloud/installer. No schema/cloud-rule change is required for the final avatar format.
- Installation and its real-profile configuration checks use the normal user's filesystem context; isolated/inspector-assisted results are labelled accordingly. Formal assurance and final hardening remain open.
