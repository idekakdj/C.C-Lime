October 3, 2026. Owner instruction: offer **both authenticator-app codes and passkeys**, plan first, then implement. Billing must stay disabled. This supersedes SMS activation as the active feature work. Existing 0.1.17 remains installed; do not change version or install without a requested release. No live SMS, billing upgrade, paid service, credential publication or owner-factor enrollment is implied.

## Product behavior and architectural decisions

Users may sign in with (1) email/password plus a six-digit authenticator code or (2) a registered passkey with Windows Hello/phone/security-key user verification. **Security review refinement: email/password accounts must enroll native TOTP before adding a passkey.** Firebase still exposes native password/enrollment APIs; a separate passkey alone cannot stop a stolen password enrolling an attacker-controlled native factor. The gateway refuses password-backed accounts lacking native TOTP, including after factor removal. Both subsequent sign-in choices remain available. A passkey-only password enrollment alternative requires a different server-owned identity/recovery policy and is outside this candidate. Google-only sign-in retains the existing policy; upstream Google MFA is not presumed. Local calendar exploration remains available without claiming account authentication.

[Firebase supports native TOTP](https://firebase.google.com/docs/auth/web/totp-mfa). Its current documented MFA enrollment/sign-in APIs support phone/TOTP, not a WebAuthn second-factor assertion. Native TOTP-enrolled password sign-in returns an opaque pending credential, not a first-factor ID token a separate passkey server can safely validate. Therefore the passkey option is a separate, user-verified cryptographic sign-in, not a fake Firebase second-factor completion or a client-side bypass of the TOTP prompt. Switching to passkey cancels the password/TOTP attempt.

Passkey registration/assertion must be verified by a trusted server shared across computers. Local SQLite verification, a renderer flag, a user-writable cloud profile flag or an unsigned JWT cannot authorize cloud access. The gateway verifies the WebAuthn challenge, exact HTTPS origin/RP ID, signature, credential binding, user presence and **user verification**, then issues a short-lived Firebase custom token for the same UID with a narrowly defined session assurance claim. The Firestore candidate permits custom-issued sessions only with that signed claim; ordinary custom/phone-only/anonymous tokens remain denied. Firebase custom tokens are documented separately from provider MFA; never label custom passkey sessions as native `sign_in_second_factor=totp`.

The owner selected **Cloudflare Workers/D1 free plan** on October 3. Continue portable/local implementation before deployment. Free tiers have request/storage/CPU limits and availability tradeoffs, not unlimited free capacity. No provider account, paid subscription, new domain, service-account key or production credential upload is created until the concrete deployment/trust configuration is reviewable. Firebase billing stays disabled even if a separate free gateway is later approved.

## Security, storage and recovery requirements

TOTP enrollment secret/session stays in main memory and appears in renderer only while displaying the setup key/QR. Never include it in a snapshot, calendar DB, backup, diagnostics, toast, log, URL, localStorage or GitHub. Clear on completion/cancel, account change and bounded expiry. QR is generated locally; do not submit the secret to an image/QR service. Never verify TOTP locally and pretend that Firebase accepted it.

Passkey private keys remain in the authenticator. The gateway stores only UID binding, credential ID/public key, counters/backup properties, user-selected name and timestamps in a separate server-only credential store. Calendar documents never contain authentication credentials. Store challenge hashes/opaque records with a five-minute expiry, operation/account/session binding and atomic one-use consumption. Use durable counters/rate limits, not worker memory or local UI limits. Do not log credential IDs, biometric data, enrollment secrets, assertions, custom tokens or user emails.

An initial passkey registration requires a verified-email, recent signed identity and fresh proof of the existing required factor where one is already registered. Adding/removing/replacing a factor requires recent full authentication, expected UID and exact operation binding. A valid old token with a compromised password must not bypass an existing factor. Last-factor removal is refused. Offer a second enrolled authenticator/passkey as recovery. Do not invent recovery codes without a server-owned, hashed, one-use and audited recovery design; Firebase does not supply that feature automatically. Password reset alone cannot remove factors or release the calendar. Lost-all-factors recovery remains a deliberate supported policy, not an email-link bypass.

Refresh/revocation is checked before online cloud access. A passkey credential's revocation and Firebase session revocation must be reflected in backend/gateway checks; stale signed ID tokens may remain usable until expiration unless a server-owned rules marker/revocation gate is added and measured. Offline local access/device compromise are separate boundaries and must remain disclosed. The eight-character password rule meets NIST's minimum-length requirement only with enforced MFA; Unicode counting/screening and other assurance gaps remain explicit. TOTP is not phishing-resistant; correctly implemented user-verified WebAuthn offers the phishing-resistant option, but neither feature alone creates NIST/SOC 2/ISO/PIPEDA certification.

## Acceptance matrix

Cross both methods with: signup/existing account, verified/unverified email, password/Google-linked/Google-only provider, configured/absent runtime config, fresh start/remembered restart, password change/reset/deletion, added/removed/replaced/last factor, offline/reconnect, pending edits, two logical/physical devices, cancellation/concurrent delayed replies and all themes/small windows.

TOTP-specific: supported provider SHA1/six digits/30 seconds, bounded adjacent intervals, leading-zero code, wrong/current/expired/reused code, secret QR/URI escaping, no persistence/export/diagnostic/browser credential-store leakage, finalization generation/UID binding and provider cooldown. Actual provider tests must be marked separately from mocks/emulators.

Passkey-specific: registration/assertion successes; invalid challenges/types/origins/RP hashes/signatures/flags/credential IDs/user handles; UV required; expired/replayed/racing/consumed tickets; attestation none/platform/cross-platform; discoverable credentials, zero counters/synced backup flags; algorithm support; payload size/depth; account enumeration; distributed request ceilings; backend unavailable; callback substitution; revocation; secret/key custody; Firebase custom-claim propagation. A virtual authenticator is protocol evidence, not a human Windows Hello/phone observation.

## Definition of done and honest activation boundaries

Both methods are complete only when a compatible app presents both working choices, the trusted backend/provider verifies them, raw cloud bypass attempts fail, enrollment/recovery/revocation work and the owner can use both on a real device with billing disabled. A staged module, mocked UI or virtual authenticator does not close live activation. Missing free-host account/stable RP address/server trust credentials or inability to use native TOTP without billing blocks only dependent activation; continue portable source/test work and prepare concrete reviewable deployment inputs. Never substitute a local flag for server verification or add Firebase billing to make tests pass.
