## Exact engineering change specification (T-50–T-52)

### T-50: service and provider retry limits

1. Use a monotonic clock and fixed, bounded policy keys. Do not use email, password, UID, titles or IP addresses as local limit keys or log their values. Denied attempts do not extend the window. Charge attempts before validation/network/notification/file-dialog side effects.
2. Shared sign-in/create/Google/link/reauth bucket: 10 attempts per 60 seconds. Shared verification/reset email bucket: 3 per 60 seconds. Profile refresh and manual sync: separate 6 per 60-second buckets. Notification test: 3 per 60 seconds. Import/restore/export/backup/diagnostic file operations: shared 10 per 60 seconds.
3. Cancellation, sign-out, local saves, reading a calendar and deleting an account remain reachable during throttling. Throttling must never discard a save or outbox mutation. Recovery/undo must remain usable.
4. Use a readable wait message rounded up to seconds. Test the first allowed attempt, exact limit, next denial, independent buckets, expiry, repeated denials, sensitive-key avoidance and bypass-free service placement before effects.
5. Cloud HTTP requests get a per-adapter 600-request/60-second safeguard. Treat provider HTTP 429 as a transient wait even if its body is not JSON. Parse Retry-After seconds/HTTP date (using provider Date when available), default 60 seconds; preserve longer waits up to a documented 24-hour safety bound. Do not retry automatically inside the same request.
6. A provider wait must survive manual retry, foreground/resume and new local saves within that sync engine. Keep queued writes pending; show a temporary limit message. Tests use injected/fake time and verify zero network calls during the hold and resumed delivery afterwards.
7. These local guards limit the shipped app; they are not an internet-wide security boundary. Firebase has provider-side authentication quotas/protections, but custom cross-device account/IP controls, global read-abuse controls, distributed signup abuse and alerting remain T-53. [Firebase authentication limits](https://firebase.google.com/docs/auth/limits).

### T-51: server-enforced calendar mutation quota

1. Limit each verified account to 60 accepted atomic calendar commits per server-timed 60-second window. An atomic commit remains one to four domain records plus a receipt and head. Group size, authorization, compare-and-swap, deleted-account guards and acknowledgement recovery stay enforced. This is a bounded burst policy, not a promise of evenly spaced writes.
2. Store `rateWindowStart` (Firestore timestamp) and `rateWindowCount` (integer 1–60) on the existing sync head. No new quota document or additional rule document lookups. Initial/expired windows must use REQUEST_TIME and count 1. Within the window retain the exact timestamp and increment by one. Clients cannot omit/decrease/reset/forge the counter or time, nor delete the active head to reset the quota.
3. Existing heads without either field migrate on their next accepted write; heads with malformed/partial quota fields fail closed. Old records remain readable. Old clients that omit these fields will be denied writes by the new rules. Upgrade the owner's installed client before live rule rollout; record this compatibility boundary prominently.
4. The client reads the quota in the same head used for compare-and-swap. Use the server Date header to estimate remaining time conservatively with a one-second margin. Preserve timestamp precision when re-sending an unchanged window. An exhausted quota yields a transient wait; lost-response receipt recovery costs no second quota token.
5. On races, read the new head and re-evaluate both quota and versions. A rule denial is not automatically treated as a quota denial: confirm unchanged saturated head before translating it to a wait. Other authorization/schema failures retain their errors.
6. Emulator tests: first write, boundary slot 60, slot 61 denied through raw REST, reset/decrement/omission/forged timestamp denied, expired-window rollover, legacy-head migration, racing clients at last slot, independent accounts, max four-record/five-reminder rule budget, retry receipt, tombstone and interrupted deletion regressions.
7. Verify new package, source/ASAR credential scans and populated upgrade fixture before deployment. Save prior rules privately for rollback. Deploy only the tested rules to the existing project; no billing changes. Use disposable test accounts for live acceptance; never fill the owner's quota or alter their calendar. Record deployed rules hash and live observed results. Rolling back removes this limit and is a security regression requiring an explicit incident decision.
8. A rules quota limits accepted account writes, not attempted reads, rejected requests, account creation, privileged Admin SDK writes or distributed abuse across accounts. Rules may incur reads for rejected operations. T-53 must close the public-service abuse gaps; do not describe this as universal DoS protection. [Firestore conditions and access-call limits](https://firebase.google.com/docs/firestore/security/rules-conditions).

### T-52: genuine 404 and recovery

1. Add a self-contained black/purple missing-page response for the packaged `cclime://app` protocol, with status 404, document language, title, main heading and a keyboard-visible Return to calendar link. No remote fonts, images, scripts or requests. Do not echo the requested path, query, credentials or filesystem errors.
2. Permit only the exact app origin and packaged renderer files with allowed extensions; reject credentials/ports, malformed encoding, backslash/colon/null traversal, escape paths and symlink escape. Missing files, directories and failed asynchronous reads must become controlled responses, not uncaught protocol rejections. GET/HEAD share status/headers; HEAD has no body. Other methods return 405 with Allow: GET, HEAD.
3. Error responses use no-store, nosniff, no-referrer and restrictive CSP. Recovery navigation is allowlisted only to the canonical app home, preserving the existing no-external-navigation boundary. IPC is accepted only from the known app document/development root, not every same-origin error page.
4. Unit tests exercise valid root/asset, unknown file/route, missing allowlisted file, invalid origin, encoded traversal, directories, asynchronous failure, HEAD/method semantics and zero path reflection. Packaged desktop tests follow the real recovery link and confirm saved data remains.
5. This app has no public hosted website. Any future website/API needs its own server-side unknown-route/404 and method tests; this screen does not create a web deployment.
