# Required MFA for password sign-in: implementation and activation gates

October 2, 2026, Ontario owner-only pilot. The owner requests SMS MFA after the current password/setup work and chooses **required for email/password accounts**. Local calendar exploration remains available. Google-only authentication is outside this password-length decision; upstream Google MFA is not presumed. No live MFA, billing, hosting or installed application change has occurred.

## Guidance and security claim

[NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html#passwordver) permits an eight-character password minimum when passwords are always part of MFA, versus fifteen for single-factor passwords. This changes only the length rule, not the rest of NIST's requirements. Current source/cloud eight-character policy without live MFA does **not** satisfy the single-factor rule. The installed 0.1.17 still uses fifteen for new passwords.

[SMS/PSTN is restricted](https://pages.nist.gov/800-63-4/sp800-63b.html#restricted-authenticators): it can be used after assessed/accepted risk, meaningful notice, an unrestricted alternative and a migration plan. SIM swapping/number porting and phishing can compromise codes. Codes from an authenticator app avoid reliance on a carrier but are also phishable. NIST AAL2 requires offering a phishing-resistant option; SMS plus a password alone is not an AAL2 conformance determination. Passkey/security-key architecture is a separate prerequisite for that claim. SOC 2/ISO/PIPEDA status remains unchanged.

The recommended implementation provides SMS **and** Firebase-native TOTP as the unrestricted alternative, requiring either factor for password sign-in. Do not implement SMS-only while claiming NIST conformance. Do not use email as the login second factor, invent shared bypass codes or store OTP/TOTP secrets in the calendar/profile.

## Verified provider constraints and unresolved dependencies

1. Existing fresh provider metadata reports Identity Platform, application MFA DISABLED and billing disabled. Re-read before any mutation; never infer administrator or Google-account MFA from this status.
2. [Firebase SMS MFA](https://firebase.google.com/docs/auth/web/multi-factor) requires verified email, supported first-factor providers, authorized web domains, SMS region policy and browser reCAPTCHA before sending codes. Electron's sandboxed custom application origin is not an already authorized HTTPS web domain. Keep its CSP, sandbox and context isolation; do not add arbitrary remote scripts or privileged remote pages to bypass browser verification.
3. [Firebase limits](https://firebase.google.com/docs/auth/limits#phone_number_sign-in_limits) state verification SMS requires the paid Blaze plan. The generic [Identity Platform quota table](https://docs.cloud.google.com/identity-platform/quotas) instead lists ten SMS/day without a billing instrument. A read-only classification at October 3 08:40:20 UTC returns an ACTIVE Firebase-registered project and billingEnabled=false, both HTTP 200. The [Firebase-specific FAQ](https://firebase.google.com/docs/auth/faq-and-troubleshooting) says Firebase projects must link billing to enable/use SMS starting September 2024. Treat that as the applicable setup gate; do not promise generic-table free SMS or claim live SMS eligibility has been tested. [Current provider pricing](https://cloud.google.com/identity-platform/pricing) lists Canada at US$0.01/SMS sent; re-read actual SKU/currency/allowances before proposing billing. These rates do not cap project-wide spending. No upgrade, billable send, budget notification or hosted deployment is authorized by a spending-preference answer alone.
4. [Firebase TOTP](https://firebase.google.com/docs/auth/web/totp-mfa) supports provider-managed enrollment/verification with Identity Platform and verified email. No secret is to be stored in synced calendar documents or logs; enrollment QR/secret appears only during setup and is cleared on completion/cancel.
5. Direct identity endpoints are public. Renderer cooldowns and a Firestore MFA check cannot prevent SMS pumping or signup farming. Verify provider region restrictions, reCAPTCHA, supported project SMS quota reduction, attempted-send/global controls, emergency disablement and delivered alerts before billing activation. A dashboard budget is an alert, not a hard spending cap. If the owner requires a guaranteed US$ ceiling and the provider cannot enforce it, use TOTP while retaining live SMS as blocked.
6. Hosting origin, operator consent/privacy wording, phone-number processing consent, secure recovery policy and billing ceiling need concrete review. Never collect a phone number or send a message merely to obtain test evidence. Start with fictional provider test numbers in a separate approved test configuration; keep test codes out of public production configuration.

## Test matrix and stop conditions

Cover raw first-factor access, fake profile/top-level MFA flags, enrolled-phone-but-no-second-factor claims, linked Google/password token distinction, unsupported factor/provider, unverified email, wrong UID and anonymous requests. Test proper SMS/TOTP owner get/list/atomic write plus preserved schema/quota/receipt/deletion rules. Emulator claim fixtures are not real SMS delivery or a cryptographic-token verification test.

Test signup, existing password account, verified/unverified email, linked password+Google and Google-only account; wrong/current/new password and confirmation; SMS/TOTP factor selection; expired/reused/wrong codes; rate limit/resend/restart; email verification flow; factor enrollment/replacement/removal; session refresh/revocation/offline; profile queue preservation; cancellation/concurrent replies; malformed provider responses; injected origin/redirect/oversized callback; phone validation and privacy; six-digit paste/accessibility; absence of secrets in browser/SQLite/GitHub/package artifacts. Re-run actual configured/absent-config fresh/restart sign-in after every changed package.

Stop dependent activation for absent billing/cost controls, unavailable HTTPS verification origin, unproven provider MFA claims/refresh behavior, incomplete recovery, live sign-in regressions, residual key/secret/provenance/release blockers, or unrelated config drift. Continue independent source/staging preparations, but do not deploy an enrollment gate that locks the owner out or label inactive MFA as finished.

The first staging implementation is `scripts/mfa-rules-candidate.mjs` with isolated `demo-cc-lime-mfa` cloud tests and an exact-change tooling check. It does not alter `cloud/firestore.rules`, default emulator rules, live rules/provider settings, the installed app or any account. Current end-user MFA remains disabled pending the ordered gates above.

October 3 independent source preparation adds `src/main/mfa-sign-in.ts`: an unwired main-process challenge component with private fields, opaque attempt/factor handles and masked phone labels. It supports the official [start](https://docs.cloud.google.com/identity-platform/docs/reference/rest/v2/accounts.mfaSignIn/start)/[finalize](https://docs.cloud.google.com/identity-platform/docs/reference/rest/v2/accounts.mfaSignIn/finalize) request shapes for SMS/TOTP through an injected trusted transport. It has a five-minute monotonic deadline plus expiry cleanup, three send attempts with a sixty-second wait including failures, five verification attempts shared across factor changes/resends, exclusive operations, abort on cancellation and rejection of late/malformed replies. No file writes, session acceptance, browser launch or network request implementation is present. The future AuthService must resolve the final provider UID/claims before accepting credentials, and provider-side limits must cover new attempts/devices; these local budgets alone are not distributed enforcement.

This component is deliberately not wired into current AuthService/IPC/renderer. Enrollment, origin-pinned rate-limited transport, browser reCAPTCHA, recovery, session/claim verification and UI integration remain required. The spending-preference question is pending; no paid activation is inferred from silence. M-01 and the M-03 component have independent staging work, not completed end-user MFA.

That is quota metadata, not current SMS entitlement or proof that this metric covers every MFA-send route. A provider-side reduction must be reviewed, independently read back and shown to cover SMS enrollment, sign-in, retries and raw clients before it is called a cost control. No quota has been changed.

For example, two billable Canada SMS/day for a 31-day month is US$0.62 in message charges at the observed rate before any free allowance/tax. This is an arithmetic planning example, not an implemented cap, guaranteed invoice or spending authorization. It may also be too restrictive for enrollment/retries, so an unrestricted authenticator alternative and clear quota-denial recovery are needed. Region allowlists must match the pilot owner's actual phone country; a `+1` prefix alone does not establish Canada.

Enabling project billing can also change metered-service exposure for the existing Firestore/hosting/identity/logging workload. An SMS-only quota cannot guarantee a whole-project US$1 or US$5 ceiling. The billing proposal must inventory all affected services and establish verified caps/alerts/emergency response, or explicitly retain billing disabled and defer live SMS. Budget notifications are not hard stops; a client-side counter or a gateway that direct provider calls can bypass is not a hard stop either.
